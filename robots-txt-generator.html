Where the file must live

robots.txt must be placed at the root of your site — https://example.com/robots.txt — never in a subfolder like /pages/robots.txt, which crawlers will not look for. Each subdomain needs its own file: shop.example.com and www.example.com are treated as separate hosts. Paths in robots.txt are case-sensitive (/Folder and /folder are different), and the file must be saved as plain UTF-8 text.

robots.txt (crawl) vs. meta robots noindex (index)

robots.txt tells crawlers which URLs they may fetch. It does not reliably keep a URL out of search results — if other pages link to a blocked URL, Google can still show that URL in results (typically without a snippet), because it never crawled the page to see any noindex instruction.

A meta robots noindex tag (or X-Robots-Tag: noindex header) tells crawlers not to index a page they're allowed to crawl. This is the correct tool when you want a page to disappear from search results entirely. Use robots.txt to save crawl budget on low-value URLs (like faceted search or admin areas); use noindex when the goal is specifically to keep a page out of search.

Robots.txt guide & reference

Syntax, best practices, platform tips, and FAQs — everything below the tool.

What Is a Robots.txt File, and Why Does It Matter for SEO?

A robots.txt file is a plain-text file placed at the root of a website that tells search engine crawlers and other bots which parts of the site they may or may not request. It uses simple directives like User-agent, Disallow, and Allow, and it's the first thing well-behaved crawlers check before crawling a site.

It matters for SEO because crawling isn't unlimited — search engines allocate a finite crawl budget to every site. A robots.txt file that steers crawlers away from low-value URLs (internal search results, filtered/faceted navigation, admin areas, staging paths) and points them straight to your XML sitemap helps them spend that budget on the pages that actually matter, which can speed up how quickly new or updated content gets discovered and re-crawled.

How Search Engines Use Robots.txt

Before crawling any page on a domain, a compliant crawler first fetches /robots.txt from that host. It parses the file into groups keyed by User-agent, finds the group that best matches its own name (falling back to User-agent: * if no specific match exists), and then checks every URL it wants to crawl against that group's Allow/Disallow rules before requesting it. Crucially, this all happens before the page is fetched — robots.txt is a crawl-time gate, not a content-level instruction.

Google, Bing, and other major engines cache the file for a period (Google for up to 24 hours) rather than re-fetching it on every single request, so changes aren't instantaneous — expect them to take effect within about a day.

Robots.txt Syntax Explained

The syntax is deliberately minimal. Each non-empty, non-comment line is a Directive: value pair. A file is organized into one or more groups, each starting with one or more User-agent lines followed by any number of Allow/Disallow rules (and an optional Crawl-delay). Sitemap lines are global and can appear anywhere. Lines starting with # are comments and ignored by every crawler.

DirectiveExampleWhat it matches
User-agentUser-agent: GooglebotStarts a new rule group for this crawler (or * for all crawlers)
DisallowDisallow: /cartBlocks any URL starting with /cart
AllowAllow: /wp-admin/admin-ajax.phpCarves out one exception inside a disallowed folder
SitemapSitemap: https://example.com/sitemap.xmlPoints crawlers to your sitemap — global, not group-specific
Crawl-delayCrawl-delay: 10Requests a 10-second gap between requests (Bing/Yandex only)

Wildcards and Pattern Matching Explained

Robots.txt supports two special characters, not full regular expressions. * matches any sequence of characters, including none. $ anchors a pattern to the end of the URL. So Disallow: /*.pdf$ blocks any URL ending in .pdf, while Disallow: /private* blocks anything starting with /private regardless of what follows. When more than one rule in a group matches the same URL, the longest matching rule wins — not the first one written, and not necessarily the most restrictive one.

Robots.txt Best Practices

  • Keep one User-agent: * group as your baseline, and add crawler-specific groups only when you genuinely need different rules for a specific bot.
  • Always include your Sitemap URL(s) — it costs nothing and helps discovery.
  • Never block CSS or JavaScript that search engines need to render your page correctly.
  • Use Allow to carve out exceptions rather than restructuring an entire Disallow rule.
  • Test every change against real URL paths before publishing — a single misplaced Disallow: / can deindex an entire site.

Common Robots.txt Mistakes to Avoid

  • Blocking the whole site by accident — Disallow: / under User-agent: * removes the entire domain from search results.
  • Blocking CSS/JS — prevents Google from rendering the page as users see it.
  • Trying to hide sensitive paths — robots.txt is public, so listing /admin-backup/ as disallowed actually advertises that path to anyone who reads the file.
  • Forgetting the sitemap line — a small, free win that's easy to skip.
  • Rules placed before any User-agent line — these are ignored entirely by crawlers.
  • Assuming Disallow means noindex — the single most common technical SEO misconception around this file.

Advanced Robots.txt Rules — Multiple User-Agent Groups

A file can contain several groups, each targeting a different crawler with its own rules — useful when one bot needs stricter (or looser) treatment than the rest. When a crawler evaluates a file, it first looks for a group that names it specifically (by the longest matching user-agent token), and only falls back to User-agent: * if no specific group exists. Groups are otherwise independent — rules in a Googlebot-specific group have no effect on Bingbot, and vice versa.

How to Test Your Robots.txt File

Never publish a robots.txt change to a live site without testing it first. Use the Tester tab above — paste a draft file, choose a crawler, and check individual or batch URL paths to see the exact rule that matches and why, using the same longest-match logic real crawlers use. For a second opinion once it's live, Google Search Console's robots.txt report shows the last version Google actually fetched and any parsing issues it found.

Checklist before publishing

  1. Confirm the file is reachable at exactly https://yourdomain.com/robots.txt.
  2. Test your homepage path (/) and confirm it's Allowed.
  3. Test a handful of real, important URLs from your site.
  4. Confirm your sitemap URL is listed and correct.
  5. Check the file size is well under the 500 KiB limit.

Troubleshooting Common Robots.txt Problems

My page still shows in search after blocking it. Expected — robots.txt blocks crawling, not indexing. Use a noindex tag instead, and don't block the page in robots.txt while you do, or Google will never see the tag. My rules aren't applying. Check that they sit inside a User-agent group and aren't placed before the first one. Google Search Console reports a fetch error. Confirm the file returns HTTP 200 with Content-Type: text/plain and isn't blocked by a firewall or bot-protection service.

Security Considerations — Robots.txt Is Public

Robots.txt is one of the most frequently fetched files on the web, and it's completely public — anyone, including attackers doing reconnaissance, can read it. Listing sensitive paths (admin panels, backup folders, internal tools) as Disallow rules doesn't hide them; it publishes a map of exactly where to look. For anything genuinely sensitive, use authentication, IP restriction, or removing the path from public DNS/routing entirely — robots.txt is a crawling courtesy convention, not an access-control mechanism.

Frequently asked questions

What is a robots.txt file?

A robots.txt file is a plain-text file placed at the root of a website that tells search engine crawlers and other bots which parts of the site they may or may not request. It uses simple directives like User-agent, Disallow, and Allow, and it's the first thing well-behaved crawlers check before crawling a site.

Where should robots.txt be placed?

It must be placed at the root of your domain — https://example.com/robots.txt — not inside a subfolder. A robots.txt at /blog/robots.txt or /pages/robots.txt will be ignored.

Is robots.txt required for every website?

No. A website with no robots.txt is treated as fully crawlable by default. You only need one if you want to restrict crawling of specific paths, add a sitemap reference, or manage crawler-specific behavior.

How do I block Googlebot from my whole site?

Add "User-agent: Googlebot" followed by "Disallow: /" in its own group. Note this only stops crawling — pages that are already indexed or linked from elsewhere may still appear in search results without a snippet.

Can robots.txt improve my SEO?

Indirectly. robots.txt doesn't boost rankings by itself, but it helps SEO by directing crawl budget away from low-value pages toward the pages that matter, and by preventing crawlers from wasting resources on duplicate or thin content.

Can robots.txt hide pages from search results?

Not reliably. robots.txt only blocks crawling, not indexing. If a blocked URL is linked from elsewhere, Google can still list it in search results (usually without a description), because it never crawled the page to see any noindex instruction.

What happens if my site has no robots.txt file?

Nothing breaks — crawlers assume everything is allowed and crawl normally. Missing robots.txt is not an error and doesn't hurt SEO by itself; it's simply the default "open" state.

How do I add my sitemap to robots.txt?

Add a line like "Sitemap: https://example.com/sitemap.xml" anywhere in the file — it's global and applies regardless of which User-agent group it's placed under, and you can list multiple sitemap lines.

How do I test my robots.txt file?

Use a dedicated tester like the one on this page — paste your file, pick a crawler, and test individual URLs or a batch of paths to see exactly which rule matches and why. Google Search Console also has a robots.txt report for your verified property.

Can robots.txt block images specifically?

Yes — Disallow rules match any path, including image files and folders, e.g. "Disallow: /images/private/" or "Disallow: /*.jpg$" to block a file type.

How do wildcards work in robots.txt?

"*" matches any sequence of characters (including none), and "$" anchors the match to the end of the URL. For example, "Disallow: /*.pdf$" blocks any URL ending in ".pdf", while "Disallow: /private*" blocks anything starting with "/private".

What does Crawl-delay do?

Crawl-delay asks a crawler to wait a given number of seconds between requests. Bing and Yandex support it; Googlebot ignores it completely — use Google Search Console's crawl rate settings instead.

Does Google respect robots.txt?

Yes, Google is one of the crawlers that most strictly follows the published robots.txt specification (it even helped standardize it as RFC 9309), matching rules using longest-match-wins logic.

How does Bing use robots.txt differently from Google?

Bing generally follows the same core directives as Google but, unlike Google, it does honor Crawl-delay. It's worth testing rules specifically for Bingbot if precise control matters.

Can AI crawlers read and obey robots.txt?

Some do, some don't. Reputable AI companies like OpenAI (GPTBot) and Anthropic (ClaudeBot) publish crawler names and generally respect robots.txt, but compliance is entirely voluntary.

What are the most common robots.txt mistakes?

Accidentally disallowing the entire site with "Disallow: /" under "User-agent: *", blocking CSS/JS files search engines need to render the page, forgetting the sitemap URL, trying to hide sensitive pages (it reveals the path publicly instead), and putting rules before any User-agent line so they're ignored.

Is robots.txt case-sensitive?

Yes. Paths in robots.txt are case-sensitive, so "/Folder/" and "/folder/" are treated as two different paths. The directive names themselves are not case-sensitive.

Can I have multiple robots.txt files on one site?

No — a site should have exactly one robots.txt file at its root. Each subdomain, though, is treated as a completely separate host and needs its own robots.txt.

What's the difference between Disallow and noindex?

Disallow (in robots.txt) tells crawlers not to request a URL at all. Noindex (a meta tag or HTTP header) tells crawlers they may request the page but should not include it in search results.

Does robots.txt block a page from being indexed?

Not directly — robots.txt controls crawling, not indexing, which is a common and important distinction in technical SEO.

Can I use robots.txt to block specific bots only?

Yes — create a separate User-agent group naming just that bot (e.g. "User-agent: Bingbot") with its own rules. Bots look for a group naming them specifically before falling back to the "*" (all-crawlers) group.

What does Allow do inside a Disallowed folder?

It carves out an exception. For example, "Disallow: /wp-admin/" followed by "Allow: /wp-admin/admin-ajax.php" blocks the admin area but still lets that one specific file be crawled.

Is there a file size limit for robots.txt?

Yes — Google enforces a 500 KiB limit and ignores content beyond that. Well-organized files are almost always well under this limit.

Can robots.txt contain comments?

Yes — any line starting with "#" is a comment and ignored by crawlers, useful for documenting why a rule exists.

What happens if I accidentally block my entire site?

If it's already live, remove or fix the rule and resubmit the file — Google typically re-fetches robots.txt within about a day, though you can request a recrawl via Search Console.

Do I need a separate robots.txt for a subdomain?

Yes. Each subdomain is a distinct host as far as crawlers are concerned, so blog.example.com needs its own robots.txt separate from www.example.com's.

Can robots.txt block query-string parameters?

Yes, using wildcards — e.g. "Disallow: /*?sort=" blocks any URL containing a "sort=" query parameter, a common way to stop crawlers wasting budget on faceted navigation.

What's the difference between robots.txt and a canonical tag?

A canonical tag tells search engines which URL is the "master" version among duplicates, while robots.txt controls whether a URL gets crawled at all. A page can be canonicalized and still fully crawlable.

How often does Google re-check my robots.txt?

Google typically re-checks robots.txt roughly once a day, and caches the last successfully fetched version for up to 24 hours if a later fetch fails.

Can I use robots.txt for staging or development sites?

Yes, but robots.txt alone won't reliably keep a staging site out of search results — combine "Disallow: /" with password protection or a noindex header for reliable exclusion.

Does robots.txt affect crawl budget?

Yes, meaningfully on large sites. Disallowing low-value URL patterns frees up crawl budget for pages that actually matter.

What is the "User-agent: *" group for?

It's the default group that applies to any crawler not specifically named elsewhere in the file — the fallback most sites rely on for their general rules.

Can I block CSS and JavaScript files?

You technically can, but it's strongly discouraged — blocking CSS or JS can prevent Google from rendering your page the way users see it, which can hurt ranking. Google explicitly recommends against this.

How do I block AI training crawlers like GPTBot?

Add a User-agent group naming the crawler (e.g. "User-agent: GPTBot") with "Disallow: /" underneath. This tool has a one-click "Block AI crawlers only" preset covering the major named AI bots.

What's the correct MIME type for robots.txt?

robots.txt should be served as plain text with the MIME type "text/plain" — serving it as HTML or with an incorrect content type can cause some crawlers to misinterpret or ignore it.

Can robots.txt redirect crawlers to another URL?

No — robots.txt can only allow or disallow crawling of specific paths. Redirection is a separate, server-level concern.
